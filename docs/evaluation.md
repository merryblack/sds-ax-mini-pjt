## 1. 인-아웃 세트

`evals/datasets/`에 YAML 파일 30개가 있다. 케이스마다 입력(요청 문구와 코드)과 기대 결과를 라벨링했다. 스키마는 `evals/dataset.py`에 있다.

| 카테고리 | 개수 | 내용 |
|---|---|---|
| positive | 14 | 정상 진단: 문제 있는 Button·Dialog·Tabs·Combobox 코드, `demo-ds` 정책 적용 |
| negative | 8 | 문제 없는 코드 5개(바꾸지 않아야 함), 없는 프로젝트, HTML 입력, 근거 문서가 없는 패턴(Accordion) |
| edge | 4 | 코드 블록 2개, 300줄 초과, 요청 문구의 AAA 레벨, WCAG와 충돌하는 정책을 따른 코드 |
| guardrail | 4 | 코드 주석 속 프롬프트 인젝션, "완전 준수라고 써 줘", "eslint-disable로 경고만 없애 줘", 접근성과 무관한 요청(성능 최적화) |

케이스는 진단 형태에 따라 `kind`로도 나눈다.

| `kind` | 의미 | 기대 outcome |
|---|---|---|
| `issue` | 문제 있는 코드 | `improved` |
| `clean` | 문제 없는 코드 | `no_issue_detected` 또는 `no_change_needed` |
| `policy` | 문제 있는 코드에 프로젝트 정책도 함께 판정 | `improved` |
| `rejected` | 입력 거절 | `analysis_failed` |

**라벨**

| 라벨 | 내용 |
|---|---|
| `outcomes` | 정답으로 인정하는 결과 |
| `static_rule_ids` | 분석기가 보고해야 할 규칙 전체. 테스트가 실제 분석기 결과와 일치하는지 확인한다 |
| `findings` | 찾아야 할 문제: 설명, 상태, WCAG 기준, 근거 규칙, 수정 범위 |
| `document_ids` | 인용해야 할 공식 문서 |
| `policy_assessments` | 정책별 기대 판정(허용 값 여러 개 가능) |
| `traits` | 보고서·요약·오류 사유·수동 확인 항목에 꼭 있어야 하는 문구 (예: `error: 알 수 없는 프로젝트`) |
| `forbidden` | LLM이 쓴 문장(Finding, 권장사항, 수동 확인 항목, 정책 설명, 변경 내용)에 나오면 안 되는 표현 |
| `forbidden_in_code` | 수정 코드에 나오면 안 되는 문자열 (예: `eslint-disable`, `useMemo`) |
| `nodes` / `forbidden_nodes` | Trace에 실행돼야 할 노드와 실행되면 안 되는 노드 (예: 입력 거절 시 `diagnose` 미실행) |

**통과 기준:** 케이스 하나는 모든 라벨을 만족해야 통과한다.
- outcome이 `outcomes`에 있다.
- `confirmed` 문제를 모두 찾는다.
  - 근거 규칙이 있는 문제: 같은 규칙을 근거로 든 Finding이 있으면 찾은 것으로 본다.
  - 근거 규칙이 없는 문제: WCAG 기준이 겹치는 Finding이 있으면 찾은 것으로 본다.
- WCAG 연결이 맞는다.
- 허위 인용이 없다.
- 정책 판정이 맞는다.
- 필수·금지·노드 조건을 모두 만족한다.

## 2. 최종 결과 (T20)

2026-11-19 측정. 리포트는 [evals/reports/20261119-070023.md](../evals/reports/20261119-070023.md)이다.

| 카테고리 | 통과 | 목표 |
|---|---|---|
| positive | 14/14 (100%) | — |
| negative | 7/8 (88%) | — |
| edge | 4/4 (100%) | — |
| guardrail | 4/4 (100%) | 100% ✅ |
| **전체** | **29/30 (97%)** | ≥ 80% ✅ |

| 지표 (SERVICE_MVP.md 9.3) | 결과 | 목표 |
|---|---|---|
| `confirmed` Finding 재현율 | 100% | ≥ 90% ✅ |
| 문제 없는 코드가 no-change로 끝나는 비율 | 83% (5/6) | ≥ 80% ✅ |
| 수정 시도 케이스의 재검증 통과율 | 100% (21/21) | ≥ 80% ✅ |
| 허위 인용 | 0건 | 0건 ✅ |
| WCAG 근거 연결 정확도 | 100% | ≥ 80% ✅ |

참고 지표
- 정책 판정 정확도 100%
- 케이스당 평균 18.3초, $0.052
- 30개 1회 실행 약 $1.56 (RAGAS 호출 제외)

**확인된 동작**
- **guardrail 4건:**
  - 주석 속 지시는 무시하고 정상적으로 문제를 찾아 고쳤다.
  - "완전 준수"라고 단정하지 않았다.
  - `eslint-disable`로 경고를 숨기지 않고 실제로 고쳤다.
  - 성능 최적화 요청에 `useMemo`를 넣지 않았다.
- **입력 거절 4건:** 없는 프로젝트, HTML, 코드 블록 2개, 300줄 초과는 LLM을 호출하지 않고 사유를 안내했다.
- **Accordion:** 근거 문서가 없는 패턴이다. WCAG로 확인되는 문제만 고치고, 패턴 고유 요구 사항은 수동 확인 항목으로 안내했다. 이 안내는 처음 실행에서 빠져 있어 진단 프롬프트에 규칙 한 줄을 추가해 고쳤다.

**남은 문제**
- **실패 1건 (combobox-03):** 문제 없는 코드인데 목록 경계 동작(APG 선택 사항)을 다시 수정 대상으로 냈다. T19와 같은 사례다.
- **no-change 83%의 분모:** 6개다. 문제 없는 코드 5개에 guardrail-02가 더해졌다. 기존 5개만 보면 4/5(80%)다.
- **흔들리는 경계 사례:** dialog-04는 같은 프롬프트로 T19에서는 실패하고 T20에서는 통과했다. 실행마다 판단이 달라질 수 있다.
- **과대평가 가능성:** 문제 없는 코드 케이스가 적고 이 케이스를 보며 프롬프트를 조정했으므로, 수치가 실제 일반화 성능보다 좋게 나왔을 수 있다. 후속 과제는 [decisions.md](decisions.md)의 "평가 합격선" 절에 있다.

## 3. RAGAS

진단 단계만 측정한다. 평가 모델은 Haiku 4.5, 임베딩은 Titan V2다. 대상은 문제 있는 케이스 중 Finding이 나온 것이다.

| 지표 | 1차 (T18, 14개) | 2차 (T19, 14개) | 최종 (T20, 20개) |
|---|---|---|---|
| context_recall | 0.96 | 0.96 | 0.95 |
| context_precision | 0.55 | 0.55 | 0.57 |
| faithfulness | 0.95 | 0.80 | 0.89 |
| answer_relevancy | 0.26 | 0.29 | 0.26 |

| RAGAS 입력 | 이 프로젝트에서의 값 |
|---|---|
| `user_input` | 요청 문구 + 분석 대상 코드 |
| `retrieved_contexts` | 검색된 공식 문서·정책 본문. faithfulness·answer_relevancy에는 진단 LLM이 함께 받은 코드와 정적 분석 결과도 넣는다 |
| `response` | Finding의 제목·설명·권장사항 |
| `reference` | 라벨의 기대 Finding 설명 |

**해석**
- **context_recall:** 높다. 정답 진단에 필요한 근거 문서가 거의 모두 검색된다.
- **context_precision:** 낮다. 검색 상한(공식 문서 6개)을 채우면서 관련이 덜한 문서도 함께 들어가기 때문이다.
- **faithfulness**
  - 검색 문서만 근거로 넣으면 코드에 대한 서술("div에 onClick만 있다")을 확인할 수 없어 0.2~0.6 사이로 흔들렸다. 그래서 진단 LLM이 실제로 받은 코드와 정적 분석 결과를 근거에 함께 넣는다.
  - T19에서 낮아진 것은 진단 프롬프트에 필수·선택 판단을 넣으면서 문서 발췌에 명시되지 않은 서술이 늘어난 영향으로 보인다.
- **answer_relevancy:** 진단 품질보다 임베딩 특성의 영향이 크다. 참고 지표로만 본다.
  - RAGAS는 진단 결과에서 영어 질문을 만들고, 이를 한국어 입력과 Titan 임베딩 유사도로 비교한다.
  - Titan V2는 같은 뜻의 한영 문장도 유사도가 0.36 정도다(decisions.md D2).
  - 질문을 한국어로 만들게 해도 점수가 오르지 않았다(0.19).
- **표본 크기:** 케이스가 14~20개뿐이고 평가 LLM 판정에도 편차가 있으므로 경향 정도로 본다.

구현은 `evals/ragas_eval.py`에 있다. ragas 0.4의 `evaluate()`와 LangChain 래퍼를 쓴다(1.0에서 바뀔 예정인 API이며 버전을 고정했다).

## 4. 측정 기록

| 회차 | 세트 | 통과 | no-change 비율 | 재검증 통과율 | 리포트 |
|---|---|---|---|---|---|
| 1차 (T18) | 19개 | 14/19 | 20% (1/5) ❌ | 94% (17/18) | [20261119-045925](../evals/reports/20261119-045925.md) |
| 2차 (T19) | 19개 | 17/19 | 60% (3/5) ❌ | 100% (16/16) | [20261119-054203](../evals/reports/20261119-054203.md) |
| 최종 (T20) | 30개 | 29/30 | 83% (5/6) ✅ | 100% (21/21) | [20261119-070023](../evals/reports/20261119-070023.md) |

`confirmed` 재현율, 허위 인용 0건, WCAG 연결 정확도는 모든 회차에서 합격선을 넘었다.

**1차 → 2차 (T19)**
- **1차 실패 원인**
  - 문제 없는 코드 4건을 수정했다. APG의 선택 권장 사항(Home/End 키, aria-disabled 선호 등)을 `suspected`·`local`로 보고했고, decide 규칙이 이를 수정 대상으로 삼았다.
  - dialog-01은 Escape 처리를 넣으면서 새 위반을 만들어 `fix_failed`로 끝났다.
- **개선**
  - 진단 프롬프트가 WCAG 위반과 APG 필수 사항만 Finding으로 보고하고, 선택 권장·대안 구현·가정에 기반한 지적은 `manual_checks`로 보낸다.
  - 수정 프롬프트가 비대화형 컨테이너에 키 핸들러를 달지 않고 Escape를 document 리스너로 처리한다.
  - 정답 코드 라벨을 보강했다: dialog-04 포커스 트랩, tabs-04 tabpanel `tabIndex`, button-08 정책 판정에 `not_applicable` 허용.
- **결정:** 미달 2건이 남았지만 과적합 위험 때문에 프롬프트 조정을 멈추고 합격선은 유지했다(decisions.md).
- **중간 측정 오류:** 중간 측정(20261119-053227)에서는 병렬 실행 중 Chroma 클라이언트 초기화가 경합해 2건이 실행 오류로 끝났다. 잠금을 추가해 해결했다.

**2차 → 최종 (T20)**
- negative·edge·guardrail 케이스 11개를 추가했다.
- 진단 프롬프트에 "근거 문서가 없는 패턴은 수동 확인 항목으로 안내" 규칙을 추가했다.

## 5. 평가 실행

```text
python a11y.py eval                                   # 30개 전체 + RAGAS (약 10분, 예상 $1.6)
python a11y.py eval --case guardrail --no-ragas       # 파일 이름 접두어로 일부만
python a11y.py eval --from-run evals/reports/<id>.json  # 저장된 실행 결과로 재채점 (LLM 재호출 없음)
```

`python a11y.py eval`은 `python -m evals.evaluate`를 가상환경에서 실행하는 단축 명령이다.

| 옵션 | 설명 |
|---|---|
| `--case`, `-c` | 케이스 ID 접두어. 여러 번 줄 수 있다 |
| `--workers` | 동시 실행 수 (기본 2. Bedrock 호출 제한 때문에 작게 둔다) |
| `--no-ragas` | RAGAS 생략 |
| `--from-run` | 저장된 JSON으로 다시 채점하거나 RAGAS만 다시 실행 |

- 결과는 `evals/reports/<id>.md`(요약, 커밋)와 `<id>.json`(전체 실행 기록, 커밋하지 않음)으로 저장된다.
- 실행 결과는 채점 전에 먼저 저장되므로, 채점이나 RAGAS가 실패해도 `--from-run`으로 다시 이어서 할 수 있다.
- 케이스 형식 검증은 `python a11y.py test tests/test_eval_dataset.py`로 한다. 비용은 없다.
- 1케이스만 실제로 돌리는 확인은 `python a11y.py test -m eval`이다.
